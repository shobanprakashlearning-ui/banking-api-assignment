API Automation Assignment: Banking Test Suite
Overview
This repository contains a functional API test automation suite for a core Banking API. The suite validates critical business behaviors across Customer Management (/customers), Account Management (/accounts), and Fund Transfers (/accounts/transfer). The framework is built using Java 11+, Maven, Rest-Assured (for HTTP interactions), Cucumber (for BDD-style test design), TestNG (as the test runner), and PicoContainer (for dependency injection).
Prerequisites
•	Java: JDK 11 or higher installed and configured in the system PATH.
•	Maven: Apache Maven 3.6+ installed and configured in the system PATH.
•	Network: Active internet connection to resolve dependencies and access the remote API environment.
•	Authentication: The current endpoints do not require explicit authentication (tokens/API keys). No credentials are required to run this suite.
Configuration
The target environment is managed without hardcoding environment details into the test classes.
•	Base URL: Configured centrally, defaulting to [https://seahorse-app-tam6f.ondigitalocean.app/bank-api](https://seahorse-app-tam6f.ondigitalocean.app/bank-api).
•	Overrides: The Base URL can be overridden at runtime via Maven system properties.
•	Security: No credentials, secrets, or sensitive configuration files are checked into source control.
Run Command
To execute the test suite from the command line, navigate to the project root directory and run:
Bash
mvn clean test
To override the Base URL dynamically during execution, use the -D flag:
Bash
mvn clean test -DbaseUrl=https://your-custom-environment-url.com/bank-api

Strategy
The test strategy prioritizes the highest-risk business functionalities: financial integrity, overdraft prevention, monetary precision, and data isolation.
•	Financial Integrity & Precision: Validated via Successful Transfer and Rejected Transfer scenarios using  double mapped accurately to enforce the "at most two decimal places" rule and ensure accurate balance deductions without truncation errors.
•	Data Isolation: Ensured by enforcing independent, synthetic data generation for every test run, preventing cross-contamination in the shared environment.
Design Trade-offs
•	Cucumber (BDD): Chosen to provide clear, business-readable documentation of the API contract and expected behaviors, though it adds a layer of abstraction compared to pure TestNG.
•	PicoContainer: Used for state sharing between step definitions instead of static variables. This ensures thread safety and isolates test data context per scenario.
•	Reporting Simplification: Advanced reporting libraries (like ExtentReports or Allure) were omitted to prioritize core test logic and remain within the timebox. Standard TestNG reports are utilized instead.
Data Management
•	Synthetic Data: All customers and accounts are generated dynamically with randomized attributes (e.g., fake names, random IDs) to avoid collisions with existing database records.
•	Cleanup: An @After Cucumber hook is implemented using the shared TestContext. It executes the DELETE /customers/{customerNumber} endpoint to tear down the specific records created during that scenario, ensuring the environment remains clean even if assertions fail.
Assumptions
Where the OpenAPI contract or assignment instructions left behavior unspecified, the following assumptions were engineered into the assertions:
•	Unknown Customer Reference: Querying a non-existent customer via GET will return a 404 Not Found (rather than a 500 Server Error).
•	Duplicate Account Number: Attempting to create an account with an already existing account number via POST will be rejected with a 400 Bad Request or 409 Conflict.

Omissions
Due to the strict timebox, the following items were intentionally omitted:
•	Custom HTML/Allure reporting dashboards.
•	Parallel execution configuration (Surefire forks/threads).
•	Continuous Integration (CI) pipeline YAML files (e.g., GitHub Actions).
•	Exhaustive edge-case permutations on field validation (e.g., extreme string lengths on customer names).
